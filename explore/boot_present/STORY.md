**제목: 정합된 조건에서 두 라이브러리의 CKKS 부트스트래핑 성능 차이**

**주제는 속도다. 정밀도는 보조축이다.**
수치는 전부 `PRESENT_DATA.md`, 그림은 이 폴더의 PNG 9장. 해석 주의는 `CAVEATS.md`.
⚠️ pptx 는 별도 세션에서 만든다. 이 문서는 그 입력이다.

⚠️ **S6 을 3부 앞에 두는 것이 이 구성의 핵심**이다. 3.30배를 보여주기 **전에**

## 1부 — 왜 정합인가 (3장)

### S1. 배경 — 부트는 8-op 과 다른 세트다
- **담을 내용**: 8-op(A~D)은 *연산 1회 지연시간*(μs), 부트는 *갱신 1회*(초). 단위·스키마가 달라
  통합 CSV 에 병합하지 않는다 / **SEAL 은 CKKS 부트스트래핑을 지원하지 않는다 → 2자**
- **그림/표**: 없음 (텍스트 슬라이드)
- **한 줄**: 3자 구도가 여기서는 성립하지 않는다.

### S2. 선행 연구가 남긴 자리
- **담을 내용**: Ozilgili et al.(ISCTürkiye 2025)이 결론에서 *"공정한 비교를 위해서는 추가적인
  세부사항과 파라미터 선택이 필요하므로 부트스트래핑 평가를 향후 과제로 남긴다"*
- **그림/표**: 없음
- **한 줄**: 그들이 미룬 **파라미터 정합**이 우리 §8 방법론이 다루는 영역이다.

### S3. ⚠️ 참조 논문의 표조차 정합돼 있지 않다
- **담을 내용**: Bossuat et al. Table 5.8 의 Set I(Lattigo, q₀45/Δ35/L10) 과
  Set II(OpenFHE, q₀60/Δ58/L6) 는 **L 도 Δ 도 다르다**. 논문 §5.2 가 "라이브러리 간 비교
  목적이 아니다" 라고 명시 / 우리 도구로 재현하면 둘 다 상한 1747 을 넘는다(1804 / 2108)
- **그림/표**: §10.4 재현 대조표 (`QA.md` Q5 의 표를 그대로)
- **한 줄**: **비교의 기준선을 우리가 세워야 한다.**

## 2부 — 무엇을 맞췄나 (3장)

### S4. 고정/탐색 변수 분류
- **담을 내용**: 맞추는 것 = logN 16 · 전체 슬롯 · 비밀키 분포 · q₀ · Δ · 잔여 L /
  푸는 것 = levelBudget · dnum/PCount · EvalMod scale
  · **비밀키 분포를 맞추는 것**에 넣은 이유: 해밍웨이트가 EvalMod 의 K 와 깊이를 정한다
- **그림/표**: `PRESENT_DATA.md` §8 프리셋 명세표
- **한 줄**: 도달한 상태가 같으면 손잡이 개수가 달라도 된다 — **단, 일의 양은 같아야 한다.**

### S5. 게이트와 보안 기준
- **담을 내용**: `0 < q₀ − Δ ≤ 7` (OpenFHE correctionFactor 커플링) **AND**
  `logQP_boot ≤ 1747` (Bossuat et al. Table 5.2)
  · ⚠️ **residual 이 아니라 boot 을 본다** — 폐기된 구 측정 2371/1788 이 모두 boot 값이고
    둘 다 초과였다
  · ⚠️ 보안 기준 출처가 A~D(seal `MaxBitCount` 218/438/881)와 **다르다**
  · 한 줄: *"실제 λ 산정(Lattice Estimator)은 다음 단계"*
- **그림/표**: `PRESENT_DATA.md` §7 규칙 이전 대조표 (마지막 줄)
- **한 줄**: 보안은 **상한 조회**다. λ 를 계산한 것이 아니다.

### S6. ⚠️ 그래도 남는 비대칭 — 여기서 반드시 말한다 ★
- **담을 내용**: 맞추지 **못한** 것이 하나 있고, 그것이 뒤의 모든 수를 좌우한다.
  · Lattigo 는 **sparse 임시키(H=32) 캡슐화**로 ModUp 을 우회 → `K=16`, **EvalMod 8레벨**
  · OpenFHE 는 dense 키로 ModUp → `K_UNIFORM=512`, **EvalMod 14레벨**
  · **OpenFHE 에 "dense 메인 + sparse 임시" 모드가 없다**
    (`SecretKeyDist` 4종 중 `SPARSE_ENCAPSULATED` 는 **메인키까지** H=192 로 만든다)
  · **거꾸로 Lattigo 는 캡슐화 없이 dense 가 아예 돌지 않는다** — 9조합 전수 실패
  · → **양쪽이 같은 상태에 설 수 없는 구간**이다. 없앨 대상이 아니라 **보고할 대상**이다
- **그림/표**: 없음 (체인 도식 1개 그리면 좋음 — C2S / EvalMod / S2C 깊이 대조)
- **한 줄**: **다음 장부터 나오는 3.30배는 "같은 일" 의 3.30배가 아니다.**

## 3부 — 성능 (5장) ★ 발표의 중심

### S7. 결과 ① 부트 1회 속도
- **담을 내용**: BT1 **3.26×** / BT2 **3.30×** (1t). mt 에서는 **1.33× / 1.37×** 로 좁혀진다
  · 1t 37.13 / 37.22초(OF) ↔ 11.40 / 11.29초(LA)
  · **프리셋을 바꿔도 속도는 거의 안 움직인다**(37.13 vs 37.22) — Δ 한 칸은 정밀도 축이다
  · ⚠️ 각주 유지: **EvalMod 14 vs 8 — 같은 양의 일이 아니다** (S6 을 다시 가리킨다)
- **그림**: `boot_speed_main.png`
- **한 줄**: 격차는 **1t 3.3배, mt 1.4배**다. 스레드 모드가 결론을 바꾼다.

### S8. 결과 ② 3.30배의 분해 ★ 발표의 정직성
- **담을 내용**: OpenFHE 를 `SPARSE_TERNARY` 로 내려 본 **진단 1점**(BT2 조건, dnum 7 고정)
  · 37.22 → **25.78초**. 총 격차 25.93초 중 **설명되는 것은 최대 11.44초(44%)**
  · **잔차 14.49초(56%)는 미규명** — sparse 로 내려도 **여전히 2.28배 느리다**
  · → **"캡슐화 유무 때문" 이라고 단정할 수 없다**
  · ⚠️ 감소분은 **상한**이다: 교란 셋(boot_depth 20→16 · sizeQ 25→21 · logP 240→180)이
    함께 움직였고 **셋 다 빠르게 하는 방향**이다. dnum 은 7 로 고정해 넷째를 제거했다
  · ⚠️ **진단 목적 단발 측정이며 프리셋 후보가 아니다** — 메인키가 H=192 sparse 가 되어
    Table 5.2(uniform ternary) 상한을 적용할 수 없다
  · ⚠️ **이 진단은 한쪽에서만 가능하다** — Lattigo 는 dense 로 "올려" 잴 수 없다(S6)
- **그림**: `boot_speed_breakdown.png`
- **한 줄**: **절반 이상을 우리는 아직 설명하지 못한다.** ⚠️ "구현 품질 차이" 로 말하지 마라.

### S9. 결과 ③ 병렬 이득 — Lattigo 는 이 축 밖이다
- **담을 내용**: mt/1t — OpenFHE **0.34~0.48** / Lattigo **0.97~1.02**
  · **8-op heavy 0.51~0.76 보다 이득이 크다** — 10~60초 회로가 OMP 팀 생성·배리어를 상쇄한다
  · keygen 은 격차가 훨씬 크다: OpenFHE 66.6 → 5.7초(**11.68×**), Lattigo 14.8 → 14.5초(1.02×)
  · ⚠️ Lattigo 가 ≈1 인 것은 **성능 열위가 아니라 축 밖**이다. 그러고도 두 모드 다 더 빠르다
- **그림**: `boot_speed_mt.png`
- **한 줄**: **병렬화는 OpenFHE 만의 축이고, 그래도 격차를 뒤집지 못한다.**

### S10. 결과 ④ 분해깊이별 속도
- **담을 내용**: 최속 분해깊이가 **(라이브러리, 스레드 모드) 의 함수**다
  · OpenFHE 1t `{3,3}` → mt `{4,3}` 로 **이동**한다. Lattigo 는 **두 모드 다 `{4,3}`**
  · `{2,2}` 가 59.5초로 최악(`{3,3}` 의 1.6배) — 얕은 분해가 느리다
  · ⚠️ **회전키 수만으로 설명되지 않는다**: `{4,4}` 는 키가 33개로 가장 적은데 1t 에서 4위다.
    체인이 2레벨 길어지는 것이 상쇄한다. **회전키 수는 Lattigo 실측이고 OpenFHE 것은 미확보**
- **그림**: `boot_speed_lb.png`
- **한 줄**: **"최적 분해깊이" 를 단일 값으로 말할 수 없다.**

### S11. 결과 ⑤ dnum — 속도와 보안 여유의 교환비
- **담을 내용**: §8.5 규칙 7("dnum 최소화")의 **방향은 맞지만 비용이 선형이 아니다**
  (지수 0.52 OpenFHE / 0.44 Lattigo). 원인: HK20 의 `∝ dnum` 은 **P 고정 전제**인데
  부트에선 dnum↑ → P↓(logP 240→60 / 427→61)로 NTT 가 가벼워지는 상쇄가 작동
  · 교환비: OpenFHE 여유 +180비트(55→235)의 대가 = 부트 **+93%** / keygen +223% / RSS +154%
  · 정밀도는 거의 무관(폭 0.094)
- **그림**: `boot_dnum_tradeoff.png`
- **한 줄**: 8-op 에서 세운 규칙을 **그대로 옮기면 안 된다.** 속도는 여유로 살 수 있다.

## 4부 — 정밀도 (2장, 보조축)

⚠️ **이 부를 빼지 마라.** §9.2 — 지연시간만 인용하면 **낮은 정밀도로 얻은 이득이 감춰진다.**
Lattigo 는 3.3배 빠르면서 정밀도도 9비트 높고, **둘 다 EvalMod 깊이(S6)에서 온다.**

### S12. 프리셋 대비 — Δ 한 칸에 유불리가 뒤집힌다
- **담을 내용**: BT1 → BT2 로 Δ 를 한 칸 낮추면 **OpenFHE 11.23 → 8.85**,
  **Lattigo 15.97 → 17.90** — 방향이 반대다
  · **부트 시간은 거의 같다**(37.13 / 37.22초) → 이 대비는 **정밀도 축만 움직인다**
  · 분해깊이를 `{3,3}` 으로 통일한 이유: BT2 에서 `{4,3}` 이 +1.79비트지만 **축이 오염된다**
- **그림**: `boot_preset_compare.png` (**정밀도 패널만** 쓴다. 3패널 원본은 백업)
- **한 줄**: L 을 맞춰 **순수한 Δ 축 대비**를 만들었다.

### S13. 최대 발견 — q₀−Δ / Δ 비대칭
- **담을 내용**: 정밀도를 결정하는 **축이 라이브러리마다 다르다**
  · OpenFHE 는 **Δ** 에 반응(5.52 → 11.27), Lattigo 는 **q₀−Δ** 에 반응(14.58 → 17.90)
  · q₀−Δ=1 인 5개 Δ 에서 Lattigo 가 **전부 15.967** 로 같다
  · 기전: OpenFHE 는 FIXEDMANUAL 에서 부트 회로 전체가 Δ 크기 프라임이고 입력을 재스케일하지
    않는다 → Δ 가 근사 정밀도를 직접 정한다. Lattigo 는 부트 프라임이 단계별 독립
    (C2S 56 / EvalMod scale / S2C 39)이고 `ScaleDown` 이 `Q[0]/|m|` 을 맞춘다 →
    `LogMessageRatio`(= q₀−Δ) 가 근사 구간 안 위치를 정한다
  · ⚠️ **속도로는 이런 것이 나오지 않았다** — 두 프리셋 속도가 37.13 vs 37.22 로 거의 같다.
    **이 비대칭은 정밀도 축에서만 보인다**
- **그림**: `boot_delta_precision.png`
- **한 줄**: 같은 (q₀, Δ) 를 움직여도 **두 라이브러리가 보는 것이 다르다.** 버그가 아니라 설계 차이다.
