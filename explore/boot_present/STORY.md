## 1부 — 왜 부트인가 / 왜 정합이 필요한가 (3장)

### S1. 배경 — 부트는 8-op 과 다른 세트다
- **담을 내용**: 8-op(A~D)은 *연산 1회 지연시간*(μs), 부트는 *갱신 1회*(초). 단위·스키마가 달라
  통합 CSV 에 병합하지 않는다 / **SEAL 은 CKKS 부트스트래핑을 지원하지 않는다 → 2자**
- **그림/표**: 없음 (텍스트 슬라이드). 필요하면 A~D 표 한 줄 요약
- **한 줄**: 3자 구도가 여기서는 성립하지 않는다.

### S2. 선행 연구가 남긴 자리
- **담을 내용**: Ozilgili et al.(ISCTürkiye 2025)이 결론에서 *"공정한 비교를 위해서는 추가적인
  세부사항과 파라미터 선택이 필요하므로 부트스트래핑 평가를 향후 과제로 남긴다"*
- **그림/표**: 없음
- **한 줄**: 그들이 미룬 **파라미터 정합**이 우리 §8 방법론이 다루는 영역이다.

### S3. ⚠️ 참조 논문의 표조차 정합돼 있지 않다
- **담을 내용**: Bossuat et al. Table 5.8 의 Set I(Lattigo, q₀45/Δ35/L10) 과
  Set II(OpenFHE, q₀60/Δ58/L6) 는 **L 도 Δ 도 다르다**. 논문 §5.2 가 "라이브러리 간 비교
  목적이 아니다" 라고 명시 / 우리 도구로 재현하면 둘 다 상한 1747 을 넘는다(1804 / 2108)
- **그림/표**: `PRESENT_DATA.md` 없음 — §10.4 재현 대조표를 옮겨 쓴다
- **한 줄**: **비교의 기준선을 우리가 세워야 한다.**

## 2부 — 무엇을 맞추고 무엇을 풀었나 (2장)

### S4. 고정/탐색 변수 분류
- **담을 내용**: 맞추는 것 = logN 16 · 전체 슬롯 · 비밀키 분포 · q₀ · Δ · 잔여 L /
  푸는 것 = levelBudget · dnum/PCount · EvalMod scale
  · **비밀키 분포를 맞추는 것**에 넣은 이유: 해밍웨이트가 EvalMod 의 K 와 깊이를 정한다
- **그림/표**: `PRESENT_DATA.md` §8 프리셋 명세표
- **한 줄**: 도달한 상태가 같으면 손잡이 개수가 달라도 된다 — **단, 일의 양은 같아야 한다.**

### S5. 게이트와 보안 기준
- **담을 내용**: `0 < q₀ − Δ ≤ 7` (OpenFHE correctionFactor 커플링) **AND**
  `logQP_boot ≤ 1747` (Bossuat et al. Table 5.2)
  · ⚠️ **residual 이 아니라 boot 을 본다** — 폐기된 구 측정 2371/1788 이 모두 boot 값이고
    둘 다 초과였다. residual 만 보면 못 잡는다
  · ⚠️ 보안 기준 출처가 A~D(seal `MaxBitCount` 218/438/881)와 **다르다**. A~D 재검증은 별도 과제
  · 한 줄: *"실제 λ 산정(Lattice Estimator)은 다음 단계"*
- **그림/표**: `PRESENT_DATA.md` §7 규칙 이전 대조표 (마지막 줄)
- **한 줄**: 보안은 **상한 조회**다. λ 를 계산한 것이 아니다.

## 3부 — 결과 셋 (5장) ★ 발표의 중심

### S6. 결과 ① q₀−Δ / Δ 비대칭
- **담을 내용**: 정밀도를 결정하는 **축이 라이브러리마다 다르다.**
  OpenFHE 는 Δ(5.52 → 11.27), Lattigo 는 q₀−Δ(14.58 → 17.90)
  · q₀−Δ=1 인 5개 Δ 에서 Lattigo 가 전부 15.967
- **그림**: `boot_delta_precision.png`
- **한 줄**: **같은 (q₀, Δ) 를 움직여도 두 라이브러리가 보는 것이 다르다.**

### S7. 결과 ① 기전
- **담을 내용**: OpenFHE 는 FIXEDMANUAL 에서 부트 회로 전체가 Δ 크기 프라임이고 입력을
  재스케일하지 않는다 → Δ 가 근사 정밀도를 직접 정한다 / Lattigo 는 부트 프라임이 단계별
  독립(C2S 56 / EvalMod scale / S2C 39)이고 `ScaleDown` 이 `Q[0]/|m|` 을 맞춘다 →
  `LogMessageRatio` 가 근사 구간 안 위치를 정한다
- **그림/표**: 없음 (도식 1개 그리면 좋음 — 체인 그림)
- **한 줄**: 비대칭은 버그가 아니라 **설계 차이**다.

### S8. 결과 ② 분해깊이는 이중으로 의존한다
- **담을 내용**: Δ 에 따라 최적 분해깊이가 바뀌고 **방향까지 뒤집힌다**
  (폭 0.40 → 1.22 → 1.91비트) / 스레드 모드에도 의존 — 1t 최속 `{3,3}` ↔ mt 최속 `{4,3}`
- **그림**: `boot_lb_precision.png` + `boot_lb_time.png`
- **한 줄**: **"최적 분해깊이" 는 (Δ, 스레드 모드) 의 함수다.** 단일 값으로 말할 수 없다.

### S9. 결과 ③ dnum 규칙이 부트에서 완화된다
- **담을 내용**: §8.5 규칙 7("dnum 최소화")의 **방향은 맞지만 비용이 선형이 아니다** —
  지수 0.52(OpenFHE) / 0.44(Lattigo) / 원인: HK20 의 `∝ dnum` 은 **P 고정 전제**인데
  부트에선 dnum↑ → P↓(logP 240→60 / 427→61)로 NTT 가 가벼워지는 상쇄가 작동
- **그림**: `boot_dnum_tradeoff.png`
- **한 줄**: 8-op 에서 세운 규칙을 **그대로 옮기면 안 된다.**

### S10. 결과 ③ 보안 여유 교환비
- **담을 내용**: OpenFHE 여유 +180비트(55 → 235) 의 대가 = 부트 +93% / keygen +223% /
  RSS +154%. 정밀도는 거의 무관(폭 0.094)
- **그림/표**: `PRESENT_DATA.md` §6 dnum 표
- **한 줄**: **속도를 잃고 여유를 얻는 관계**가 정량화됐다.

## 4부 — 확정 프리셋 (2장)

### S11. BT1 · BT2
- **담을 내용**: q₀=60, 잔여 L=4, 분해깊이 `{3,3}` 공통. **Δ 만 59 ↔ 58**
  · **Δ 한 칸에 유불리가 뒤집힌다**: OpenFHE 11.23 → 8.85, Lattigo 15.97 → 17.90
  · 부트 시간은 거의 동일(37.1 / 37.2초) → **정밀도 축만 움직이는 대비**
  · 분해깊이를 `{3,3}` 으로 통일한 이유: BT2 에서 `{4,3}` 이 +1.79비트지만 **축이 오염된다**
- **그림**: `boot_preset_compare.png`
- **한 줄**: L 을 맞춰 **순수한 Δ 축 대비**를 만들었다.

### S12. 본측정 요약
- **담을 내용**: 70실행 / 700 rep / 7.5시간 / **실패 0** / 스와핑 0
  · mt/1t **0.34~0.48** (8-op heavy 0.51~0.76 보다 병렬 이득 큼), keygen **11.7배**
  · **mt 정밀도 손실 없음** −0.052~+0.014 (8-op 은 −0.13~−0.54 였다)
  · Lattigo 는 내부 병렬화가 없어 축 밖(0.97~1.02)
- **그림/표**: `PRESENT_DATA.md` §1 확정표 + §9 측정 규모
- **한 줄**: 8-op 에서 문제였던 **mt 정밀도 저하가 부트에서는 나타나지 않는다.**

## 5부 — 남은 것 (1장)

### S13. 다음 단계
- **담을 내용**: 미규명 **2건만** 언급 —
  ⑴ **격차 분해 진단**(OpenFHE × sparse × BT2 조건, dnum 7 고정) 결과, 캡슐화/K 축이

  · 다음: sparse 아암 / 부분 슬롯 아암 / A~D 재검증 / 본측정 reps 확대
- **그림/표**: 없음
