# CAVEATS — 발표 시 피해야 할 해석 오류

수치 자체는 `PRESENT_DATA.md` 가 맞다. 여기 있는 것은 **그 수치를 어떻게 읽으면 안 되는가**다.
발표 중 질문이 나오면 `QA.md` 를 함께 볼 것.

---

## 1. ⚠️ "Lattigo 가 더 좋다" 로 읽으면 안 된다

BT2 에서 Lattigo 17.90비트 vs OpenFHE 8.85비트 — **9.1비트 차이**다. 그러나:

**(a) 같은 K 에서 비교한 값이 아니다.**
Lattigo 는 **sparse 임시키(H=32) 로 우회**해 ModUp 을 돌기 때문에 `K = 16` 으로 충분하고
EvalMod 이 **8레벨**이다. OpenFHE 는 dense 키로 ModUp 을 돌아 `K_UNIFORM = 512`,
EvalMod **14레벨**이다. **라이브러리가 제공하는 구성이 달라서 생긴 차이**이지
같은 조건에서 한쪽이 우수한 것이 아니다.

**(b) 그 차이조차 절반밖에 설명하지 못한다.**
OpenFHE 를 `SPARSE_TERNARY` 로 바꾼 진단(BT2 조건, **dnum 7 고정**)에서
8.853 → **14.585비트(+5.732)** 로 올랐다. 그런데 이 상승분에는 `boot_depth`(20→16) ·
`sizeQ`(25→21) · `PCount`/`logP`(4/240 → 3/180) 가 **함께 바뀐 효과가 섞여 있고,
셋 다 정밀도를 올리는 방향**이다.
→ **총 9.048비트 중 설명되는 것은 최대 5.732비트(63%), 잔차 3.316비트는 미규명**이다.

**말할 때**: "Lattigo 가 정밀도가 높다" ❌ →
**"두 라이브러리가 제공하는 부트 구성이 달라 EvalMod 깊이가 14 대 8 로 갈리며, 그 결과
정밀도가 9.05비트 차이 난다. 그중 설명 가능한 것은 최대 5.73비트다."** ✅

**(c) ⚠️ 부트 시간은 설명이 더 약하다 — 과반이 미규명이다.**
같은 진단에서 부트 시간이 37.22 → **25.78초**로 줄었다.

| | 속도 | 정밀도 |
|---|---|---|
| 총 격차 (OpenFHE ↔ Lattigo) | **25.93초** (3.30배) | **9.048비트** |
| 설명되는 것 (**상한**) | 11.44초 = **44%** | +5.732비트 = **63%** |
| **잔차 (미규명)** | **14.49초 = 56%** | **3.316비트** |

**sparse 로 내려도 Lattigo 보다 여전히 2.28배 느리다.**
→ **"속도 격차가 캡슐화 유무 때문" 이라고 단정할 수 없다.**
⚠️ **"구현 품질 차이" 로 설명하지 마라** — 우리는 그것을 잰 적이 없다.

**(d) 이 진단은 한쪽에서만 가능하다.**
OpenFHE 는 sparse 로 **내려** 진단할 수 있으나, Lattigo 는 dense 로 **올려** 진단할 수 없다 —
캡슐화 off 가 9조합 전수 실패했기 때문이다. 대칭 진단이 불가능하다는 사실 자체가
"양쪽이 같은 상태에 설 수 없는 구간이 남는다" 를 보여준다.

## 2. ⚠️ 부트 시간은 reps 10 기준이다 — 8-op 은 reps 30 이었다

| | reps | warmup |
|---|---:|---:|
| 8-op (A~D) | **30** | 3 |
| 부트 (BT1/BT2) | **10** | 3 |

부트 1회가 11~59초라 reps 30 이면 조합당 30분을 넘는다. 70실행이면 감당이 안 된다.

**따라서 8-op 표와 부트 표의 σ 를 나란히 놓고 "어느 쪽이 안정적이다" 라고 말하면 안 된다.**
표본 수가 다르다. 부트 CV 는 1t 0.002~0.03 / mt 0.03~0.09 로 충분히 작지만,
그것은 **reps 10 기준의 값**이다.

⚠️ 또 하나 — **2단계(reps 3) 값과 3단계(reps 10) 값을 섞지 마라.** 예를 들어
"Δ=59 에서 11.25비트" 는 2단계 스크리닝 값이고 3단계 확정값은 11.231비트다.
발표에는 **3단계 값**을 쓰고, 곡선(2단계)은 곡선으로만 쓴다.

## 3. ⚠️ 보안은 "표 조회" 이지 실제 λ 산정이 아니다

우리가 한 것: `logQP_boot ≤ 1747` 인지 확인.
1747 은 **Bossuat et al., IACR ePrint 2024/463, Table 5.2** 의
(λ=128, uniform ternary, σ=3.19, N=65536) 상한이다.

**하지 않은 것**: `lattice-estimator` 로 실제 λ 를 계산하지 않았다.
"여유 55비트" 는 **상한까지의 비트 여유**이지 보안 비트가 아니다.

⚠️ 추가로 두 가지 한계:
- **A~D 와 판정 근거가 다르다.** A~D 는 `seal::CoeffModulus::MaxBitCount(tc128)`
  (218/438/881) 기준이다. SEAL 의 그 함수는 N=32768 이 최대라 logN 16 상한을 주지 못한다.
  **두 세트의 보안 판정을 같은 표에 섞으면 안 된다.**
- **캡슐화 임시키(H=32)의 보안은 우리가 검증할 수단이 없다.** 그 키는
  `q₀ + p₀ ≈ 116비트` 위에만 살고(`keys.go:131-135`) 메인키는 dense 그대로라
  Table 5.2 적용이 유지될 여지가 있으나, sparse 키 자체의 안전성은
  Lattice Estimator 가 sparse 공격 비용을 지원하지 않아 확인 불가다.

**말할 때**: "128비트 보안을 확인했다" ❌ →
**"Table 5.2 의 λ=128 상한 이내임을 확인했다. 실제 λ 산정은 다음 단계다."** ✅

## 4. ⚠️ 분해깊이 순서를 단일 값으로 말하면 안 된다

**정밀도 최적 분해깊이가 Δ 마다 다르고 방향까지 뒤집힌다:**

| | Δ=52 | BT1 Δ=59 | BT2 Δ=58 |
|---|---|---|---|
| 최고 | `{3,4}` | `{3,3}` | `{4,3}` |
| 최저 | `{4,3}` | `{4,4}` | `{3,4}` |
| 폭 | 0.400 | 1.217 | 1.905 |

**속도 최적도 스레드 모드마다 다르다:** 1t 최속 `{3,3}`(37.1초) ↔ mt 최속 `{4,3}`(13.7초).
`{4,4}` 는 회전키가 33개로 가장 적은데 1t 에서 4위다 — 체인이 2레벨 길어지는 것이 상쇄한다.

→ **"분해깊이 X 가 최적이다" 라고 말할 수 없다.** (Δ, 스레드 모드) 를 명시해야 한다.
우리가 `{3,3}` 을 고른 것은 최적이어서가 아니라 **BT1↔BT2 를 순수한 Δ 대비로 유지하기
위해서**다(BT2 에서는 `{4,3}` 이 +1.79비트 더 좋다 — 이 사실을 숨기지 말 것).

## 5. ⚠️ 잔여 L=4 를 "부족하다" 로 읽지 마라 (부가)

L=4 는 **Δ 를 크게 잡은 결과**다. Δ 를 낮추면 L 은 늘지만 OpenFHE 정밀도가 급락하고
Δ ≤ 50 에서는 아예 파탄난다. **L 과 정밀도가 교환 관계**이며 우리는 정밀도 쪽을 택했다.
격자상 공통 최대 L 은 13 이고 이는 논문 Set I(L=10)을 넘는다.

## 6. ⚠️ 프로브 이탈 13건을 "측정 오염" 으로 설명하지 마라 (질문 대비)

전부 OpenFHE mt 의 **post 프로브** 이고 pre 는 13건 모두 정상이었다.
16코어가 동시에 놀면 post 프로브(약 1.1초)가 도는 동안 DVFS 가 base 로 내려간다.
부트 시간 CV 가 0.032~0.086 이고 이중 분포가 없으며 mt/1t 가 0.34~0.48 로 **1t 보다 빠르다** —
측정 중 base 였다면 느려졌어야 한다. §8.6-1 의 "프로브 실패가 곧 측정 오염은 아니다" 와 같다.
