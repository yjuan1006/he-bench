## Q1. 왜 잔여 L 이 4밖에 안 되나?

**Δ 를 크게 잡은 결과다. L 과 정밀도가 교환 관계다.**

- 부트 체인은 `q₀ + Δ × (잔여L + 부트깊이)` 다. BT1 은 Δ=59, 부트깊이 20 이라
  잔여 L=4 만 해도 `logQP = 1716` 으로 상한 1747 에 여유 31비트뿐이다.
- Δ 를 낮추면 L 은 늘지만 **OpenFHE 정밀도가 급락**한다: Δ=52 → 5.52비트, Δ=59 → 11.27비트.
  그리고 **Δ ≤ 50 은 아예 파탄**난다(자릿수 4~6배).
- 격자상 양쪽 동시 가능한 **최대 L 은 13** 이고, 이는 **논문 Set I(L=10)을 넘는다.**
  L 이 구조적으로 부족한 것이 아니라 **우리가 정밀도를 택한 것**이다.

⚠️ 덧붙일 것: 잔여 L 을 제약하는 쪽은 **OpenFHE** 다. Lattigo 는 (마) 구성에서 EvalMod 8 이라
같은 점에서 logQP 1404 로 여유 343비트다.

## Q2. OpenFHE 정밀도 8.85비트는 너무 낮지 않나?

**부트 후 정밀도는 구조적으로 이 대역이다. 8-op 의 25비트 하한은 부트에 적용되지 않는다.**

- 참조 논문의 값도 같은 대역이다 — Table 5.8 Set II(OpenFHE)가 **12.0비트**, Set I(Lattigo)가 15.9비트.
- 우리 BT1(Δ=59)은 **11.23비트**로 Set II 에 0.78비트까지 접근한다. BT2(Δ=58)가 8.85인 것은
  **Δ 를 한 칸 낮췄기 때문**이고, 그 대신 Lattigo 가 15.97 → 17.90 으로 오른다.
- 남은 격차의 성분: **입력 분포 정규화 약 1~1.6비트**(우리는 실수 x∈[−1,1), `mean|x|≈0.5`)
  + 버전 차이(v1.2.0 ↔ v1.5.1, EvalMod 레벨이 이미 +1 어긋난다).
  **flooding noise 는 원인이 아니다** — OpenFHE 기본이 `EXEC_EVALUATION` + `FIXED_NOISE_DECRYPT`
  로 꺼져 있고, 켜지면 정밀도가 **내려가므로 방향도 반대**다.

⚠️ **8-op 처럼 "정밀도 하한 25비트" 게이트를 부트에 세우지 않았다.** 세우면
(Δ, L, 정밀도) 교환비 곡선의 절반을 못 보게 되고, 그 곡선이 2단계의 결과물이었다.

## Q3. 그럼 Lattigo 가 더 좋은 건가?

**아니다. 같은 조건에서 비교한 값이 아니다.** (`CAVEATS.md` 1번)

- Lattigo 는 **sparse 임시키(H=32)로 우회**해 ModUp 을 돌아 `K=16`, EvalMod **8레벨**.
  OpenFHE 는 dense 키로 돌아 `K_UNIFORM=512`, EvalMod **14레벨**.
  → **OpenFHE 에는 "dense 메인 + sparse 임시" 모드가 아예 없다**
  (`SecretKeyDist` 4종 중 `SPARSE_ENCAPSULATED` 는 메인키까지 H=192 로 만든다).
- 반대로 **Lattigo 는 캡슐화 없이는 dense 가 아예 돌지 않는다** — 9조합 전수 실패했다.
- 즉 **양쪽이 같은 상태에 설 수 없는 구간**이 남는다. 이것은 부트 깊이 +1,
  부트 회로 프라임 크기 비대칭과 **같은 계열**이며 **없앨 대상이 아니라 보고할 대상**이다.

**정량 확인** (BT2 조건, dnum 7 고정 진단):

| | 속도 | 정밀도 |
|---|---|---|
| 총 격차 | **25.93초** (3.30배) | **9.048비트** |
| 설명되는 것 (**상한**) | 11.44초 = **44%** | +5.732비트 = **63%** |
| **잔차 (미규명)** | **14.49초 = 56%** | **3.316비트** |

→ sparse 로 내려도 Lattigo 보다 **여전히 2.28배 느리다.** 속도는 과반이 미규명이다.
⚠️ **"구현 품질 차이" 로 답하지 마라** — 잰 적이 없다.
⚠️ 이 진단은 **한쪽에서만 가능하다** — Lattigo 는 캡슐화 off 가 동작하지 않아 대칭 진단이 불가능하다.

## Q4. 보안은 확인했나?

**`logQP_boot ≤ 1747` 을 확인했다. 실제 λ 는 계산하지 않았다.**

- 1747 은 Bossuat et al., ePrint 2024/463, **Table 5.2** 의 (λ=128, uniform ternary,
  σ=3.19, N=65536) 상한이다.
- **⚠️ residual 이 아니라 boot 을 본다.** 폐기된 구 측정에서 OpenFHE 2371 / Lattigo 1788 이
  나왔는데 **둘 다 boot 값이고 둘 다 초과**였다. residual 만 보면 못 잡는다.
- BT1 여유 31비트(OF) / 339비트(LA), BT2 여유 55 / 343 비트.

**한계 셋을 함께 말할 것**:
1. **표 상한 조회이지 λ 산정이 아니다.** `lattice-estimator` 는 SageMath 환경이 필요해 다음 단계다.
2. **A~D 와 판정 근거가 다르다.** A~D 는 `seal MaxBitCount`(218/438/881) 기준이고
   그 함수는 N=32768 이 최대라 logN 16 을 못 준다. A~D 재검증은 **별도 과제**다.
3. **캡슐화 임시키(H=32)의 보안은 검증 수단이 없다.** 그 키는 `q₀+p₀ ≈ 116비트` 위에만 살고
   메인키는 dense 그대로지만, sparse 키 자체는 Lattice Estimator 가 지원하지 않는다.

## Q5. 논문 Table 5.8 과 왜 다른가?

**두 성분으로 나뉜다. 하나는 규명됐고 하나는 버전 차이다.**

| | 논문 | 우리 재현 | 차 | 원인 |
|---|---:|---:|---:|---|
| **Set II** logQ | 1511 | 1568 | +57 | **EvalMod 1레벨**(14 vs 13) |
| **Set II** logP | 180 | 540 | +360 | ⚠️ **dnum 표기 해석** — 아래 |
| **Set I** logQ | 1464 | 1499 | +35 | EvalMod 1레벨 |
| **Set I** logP | 305 | 305 | **0** | — |

**⚠️ 논문의 "dnum" 은 `numPerPartQ`(digit 당 타워 수) 로 읽어야 한다.**
`numPartQ`(digit 개수)로 읽으면 perPart 9 → digit 524비트 → PCount 9 → logP 540 이 되는데,
`numPerPartQ = 3` 으로 읽으면 digit 176비트 → PCount 3 → **logP 180 으로 정확히 맞는다.**
체인 길이까지 맞추면 **logQ 1510 / logP 180 / logQP 1690** 으로 논문(1511/180/1691)과
**1비트 차이**다 — 명목 `round(log2)` 관례 차이다.

**남는 것**: 양쪽 다 EvalMod 이 +1레벨이다(v5.0.2/v1.2.0 ↔ v6.2.0/v1.5.1 버전 차이).
Set I 의 S2C·C2S 배분 8~25비트는 논문 측 스케일 설정을 알 수 없어 **미규명**이다.

⚠️ **두 세트를 프리셋으로 베끼면 안 된다.** 우리 도구로 재현하면 둘 다 상한을 넘고
(1804 / 2108), 논문 §5.2 도 "라이브러리 간 비교 목적이 아니다" 라고 명시한다.

## 그 밖에 나올 만한 것

### Q6. 왜 SEAL 이 없나?
**SEAL 은 CKKS 부트스트래핑을 지원하지 않는다.** 8-op 의 3자 구도가 여기서는 성립하지 않는다.

### Q7. mt 에서 정밀도가 떨어지지 않나?
**8-op 에서는 OpenFHE 만 −0.13~−0.54비트였는데, 부트에서는 −0.052~+0.014 로 나타나지 않는다.**
전 10조합 최악이 −0.052비트다. 설명은 추정이다 — "8-op 은 op 1회(μs)라 OMP 스케줄링 지터의
상대 비중이 크지만 부트는 15~37초 단일 회로라 평균화된다" 로 보이나,
**8-op §8.7 의 원인 자체가 미검증**이라 확정할 수 없다.

### Q8. 왜 reps 10 인가? 8-op 은 30 이었는데.
부트 1회가 11~59초라 reps 30 이면 조합당 30분을 넘고 70실행이면 감당이 안 된다.
CV 는 1t 0.002~0.03 / mt 0.03~0.09 로 충분히 작다.
⚠️ **8-op 표와 σ 를 나란히 비교하면 안 된다** — 표본 수가 다르다.

### Q9. 분해깊이는 왜 {3,3} 인가? BT2 에서는 {4,3} 이 더 좋다던데.
맞다. BT2 에서 `{4,3}` 이 **+1.79비트**다. 그래도 `{3,3}` 을 쓴 이유는 셋:
① **축 오염** — BT1↔BT2 를 "L 같고 Δ 만 다른 순수 대비" 로 설계한 것이 프리셋 2점의 존재 이유다
② **대가가 크다** — 부트는 +2% 지만 keygen 2.25배(64.8→145.9초), RSS 1.8배(15.5→27.6 GB)
③ **순서 역전 자체가 결과다** — 프리셋마다 최적을 쫓으면 그 관찰이 표에서 사라진다
그리고 `{3,3}` 은 1t 최속이고 mt 에서도 2위(최속 대비 +9%), RSS 는 5종 중 최소다.

### Q10. 실패한 측정은 없었나?
**3단계 700 rep 전부 성공, 스와핑 0건.** 2단계에서는 126 rep 중 3 rep 실패
((q₀=53, Δ=52, L=3, {3,3}), 자릿수비 2.443) — 같은 L 의 다른 네 분해깊이와
같은 `{3,3}` 의 L=4~7 은 전부 정상이라 **고립 실패이며 미규명**이다.
