## 1. ⚠️ `digit` 열의 라이브러리별 정의 감사 (B-2 — 다른 모든 판정의 전제)

`scripts/v3_unify.py` 는 원본 CSV 의 `digits` 문자열(`L12=3;L11=3;…`)을 레벨별로 펼 뿐이고, 그 문자열은 **각 벤치 하네스가 서로 다른 규칙으로** 만든다.

| library | digit 정의 (소스 근거) |
|---|---|
| openfhe | min(dnum, ceil((L+1)/perPart)) — 런타임 GetNumPartQ/GetNumPerPartQ 기반 (실제 digit 수) |
| lattigo | min(dnum, ceil((L+1)/#P)) — API 부재로 하이브리드 규칙을 밖에서 재구성 |
| seal | L+1 — 항등식(특수소수 1개, Q 프라임 1개당 digit 1개). 관측값 아님 |

근거 위치: `src/presetsearch_openfhe.cpp:216-222` · `src/presetsearch_lattigo.go:283-288` · `src/presetsearch_seal.cpp:169-171`

## 2. 한계 이득비 g(L) = mean_us(L) / mean_us(L+1) 전수 계산

- 기대 쌍 수 = Σ(depth−1) × 3 × 2 × 8 = **1344**  →  실제 **1344쌍** (일치)
- 레벨 불연속으로 제외한 쌍: **0건**
- cv 게이트(>0.05) 통과: **1119쌍** / 게이트 걸림 **225쌍** (그 중 cv>0.2 오염 의심 **97쌍**)
- key-switch op 쌍: **504** / 대조군 쌍: **840**
- g < 1 이면 레벨을 내려 빨라진 것, g ≈ 1 이면 **내려도 안 빨라진 것**(포화)

## 9. 주장별 판정

> §0~§8 의 표는 스크립트가 자동 산출한 숫자다. 아래 §9 는 그 숫자를 읽고 쓴 **결론**이다.

### (A) 저레벨 포화 — **부분 성립** (지시된 판정 기준으로는 불성립, 물리 기전은 확인)

**지시된 기준으로는 성립하지 않는다.** 기준은 "OpenFHE 의 g(L) 이 저레벨에서 유의하게 1.0 에 접근" 이었으나, 데이터는 **정확히 반대 방향**이다.

- Spearman ρ(level, g) 가 **모든 라이브러리에서 양수**다 (1t 중앙값: OpenFHE 0.55 · Lattigo 0.50 · SEAL 1.00). ρ<0 인 (preset×op) 그룹은 **36개 중 0개**. 비계단 쌍만 봐도 ρ 중앙값 0.87~0.95 로 더 강하게 양수다.
- 저레벨 g 는 고레벨 g 보다 **1.0 에서 더 멀다**. 12개 (preset×library) 조합 중 "저레벨이 1 에 더 가깝다" 는 **0개**. (예: A·OpenFHE 저레벨 0.835 / 고레벨 0.925)
- 이유는 기전이 아니라 기하다. 적합 모델 `a·(L+1)·digit + b` 가 R² 0.99 로 맞는데, digit 이 1 로 포화한 저레벨 구간에서 g(L) = (a(L+1)+b)/(a(L+2)+b) 이고 이 값은 L 이 작아질수록 **작아진다**. 즉 레벨을 내릴 때의 **상대 이득은 저레벨에서 오히려 커진다**. "내려도 덜 줄어드는 구간" 은 이 데이터에 없다.

**같은 데이터가 지지하는 것** — 고정비 자체는 실재하고, 라이브러리를 가른다:

- 절편 b 는 같은 logN·같은 op 에서 **OpenFHE 가 SEAL 의 2.28~3.11배**, Lattigo 가 1.53~2.13배다 (4프리셋 전부, §3.4). PCount 는 OpenFHE 2~5 · Lattigo 2~5 · SEAL 1 이다.
- 레벨을 바닥까지 내렸을 때 남는 비율 `mean(L=1)/mean(maxL)` 은 **4프리셋 전부에서 OpenFHE > SEAL** (0.159/0.193/0.244/0.438 대 0.056/0.172/0.076/0.290, §3.5). OpenFHE 는 레벨을 다 내려도 SEAL 보다 많이 남는다.
- ⚠️ 단, 이 차이는 **저레벨에 몰려 있지 않다**. |1−g| 의 OpenFHE/SEAL 비가 저레벨과 고레벨에서 거의 같다(위 표). 라이브러리 차이는 **곡선 전체의 기울기 차이**이지 특정 레벨 구간의 국소 현상이 아니다.

**논문에 대한 함의:** 4.2절을 "저레벨에 포화 구간이 존재한다" 로 쓰면 **데이터에 반한다**. 살릴 수 있는 형태는 "OpenFHE·Lattigo 는 레벨 무관 고정비(P 운반)가 SEAL 의 2~3배여서 레벨 하강으로 회수 가능한 비용의 비율이 구조적으로 작다" 이며, 근거는 g(L) 이 아니라 절편 b 와 바닥 비율이다. 4.2절이 통째로 사라지지는 않지만 **주장·지표·그림을 모두 갈아야 한다.**

### (B) SEAL 의 매끄러움 — **부분 성립** (비용 쪽은 성립, digit 쪽은 동어반복)

- **digit 쪽(B-1)은 검증이 아니다.** SEAL 하네스는 `digit = level+1` 을 그냥 출력한다(`src/presetsearch_seal.cpp:169-171`). "SEAL 에서 digit 이 레벨에 선형 증가하고 계단이 없다" 는 관측이 아니라 **정의의 재진술**이다. 논문에서 이를 실측 결과로 제시하면 안 된다. Lattigo 열도 라이브러리가 노출하지 않는 값을 밖에서 재구성한 추정치다(§1).
- **비용 쪽(B-3)은 성립한다.** SEAL 의 g(L) 은 레벨의 **완전 단조 함수**다 — Spearman ρ(level,g) = 1.000 이 12개 (preset×op) 그룹 **전부**에서 나온다. 같은 지표가 OpenFHE 0.55 · Lattigo 0.50 으로 비단조다. 즉 SEAL 의 레벨-비용 곡선에는 **불연속 점프가 없고**, OpenFHE·Lattigo 에는 있다. 이것이 대조군으로서 유효한 실측 진술이다.
- 이봉성은 g 분포의 갭 통계로는 잘 갈리지 않는다(`gap_ratio` 0.20~0.79, 라이브러리 간 구분 안 됨, §4.2). 이봉성의 증거는 갭이 아니라 **계단/비계단 분류의 완전 분리**(§5.5)다.

### (C) 계단 크기 — **성립** (기억 수치는 한쪽이 틀렸다. 아래로 확정)

cv 게이트(>0.05) 통과, key-switch op(rot1·relin·mul_cc_rlk), OpenFHE·Lattigo 기준:

- **계단 전이**: g ∈ [0.542, 0.753], 중앙 0.668, n=45
- **비계단**:   g ∈ [0.782, 1.010], 중앙 0.898, n=123

- 기억 속 **계단 0.54~0.73 → 실측 0.542~0.753** (거의 맞음, 상한만 소폭 확장).
- 기억 속 **비계단 0.81~0.93 → 실측 0.782~1.010** (⚠️ **틀렸다**. 실제 범위가 양쪽으로 넓고, 특히 상한이 1.0 을 넘는 쌍이 있다 — A·Lattigo·mul_cc_rlk 의 g=1.010, 레벨을 내렸는데 오히려 느려진 쌍이다). 논문에 0.81~0.93 을 쓰면 안 된다.
- **네 프리셋 전부에서 재현된다.** (preset × library) 8개 조합 **전부에서 계단 최대값 < 비계단 최소값** — 완전 분리다(§5.5).
- **대조군이 정확히 대조군답게 나온다.** key-switch 없는 op 는 digit 전이 여부로 g 가 갈리지 않는다 (OpenFHE 계단 중앙 0.800 vs 비계단 0.834, 범위 완전 중첩; §5.4). 계단 신호는 key-switch 경로에서만 나온다 — 기전 귀속이 확인된다.
- ⚠️ **SEAL 은 이 분류에서 빠져야 한다.** 정의상 모든 쌍이 '계단' 이라 대조가 성립하지 않는다.

### (D) mt 의 reps 실태 — **단일 실행 확정. 재측정 시 필수 수정 항목.**

- CSV 의 `reps` 는 **1536행 전부 30** 이고, 이는 **한 프로세스 안의 반복 횟수**다. 프로세스 반복 횟수를 나타내는 열은 이 CSV 에 **없다**.
- 수집 스크립트 확인 결과 **A·B·C(`run_main_mt.sh`)·D(`run_main_D.sh`) 의 mt 는 전부 라이브러리당 프로세스 1회 실행**이고, `v3_unify.py` 는 median 을 취하지 않는다. → **v3 요약의 mt 열은 5-run median 처리를 거치지 않았다.**
- 이것이 실제로 위험한 크기임을 같은 저장소의 반복 런 자료가 보여준다: OpenFHE mt 의 런 간 산포 `(max−min)/median` 이 key-switch op 에서 **중앙 0.208 · 최대 0.459**다. 단일 런이 어디에 떨어졌는지로 결론이 뒤집힐 수 있다.
- 요약 CSV 자체에서도 같은 결론이 나온다: **mt·OpenFHE·key-switch 쌍 84개 중 cv≤0.05 를 통과하는 것이 0개**다. 이 조합은 현재 데이터로 정량 분석이 **불가능**하다 (본 보고서의 mt·OpenFHE 칸이 전부 비어 있는 이유).
- ⚠️ **4.1절(스레드 축) 재측정 시 필수:** mt 는 라이브러리당 최소 5회 프로세스 실행 후 median 을 쓰고, 프로세스 반복 수를 CSV 열로 남길 것. 현재 mt 값으로 4.1절을 쓰면 안 된다.

### 부수 — preset C · OpenFHE 정밀도 예외값

**확인됨.** ks_loss 레벨 간 변화폭 **0.813비트**(1t) / 0.978비트(mt)로, 다른 11개 (preset×library) 조합의 0.008~0.014비트보다 두 자릿수 크다. 정체는 완만한 레벨 의존이 아니라 **L5↔L4 의 단일 계단**(L10~L5 ≈ 4.09비트, L4~L1 ≈ 3.28비트, 약 3.8σ)이다. 다만 OpenFHE C 의 digit 전이는 L6→L5 로 **한 레벨 어긋나** 있어 digit 계단으로 바로 귀속시킬 수 없다. 논문에 넣으려면 별도 확인이 필요하다.
