### 1.3 판정 — 분리 폭 `min(비전이 g) − max(계단 전이 g)`

양수면 두 분포가 완전 분리, 0 이하면 겹친다.

| 부류 | 분리폭_OWN | 분리폭_OF |
|---|---|---|
| key-switch (참조) · 게이트 적용 | +0.0282 | -0.2449 |
| key-switch (참조) · 게이트 미적용 | +0.0282 | -0.2449 |
| 대조군 5 op · 게이트 적용 | -0.4805 | -0.4975 |
| 대조군 5 op · 게이트 미적용 | -0.5176 | -0.5346 |
| 대조군 4 op · 게이트 적용 | -0.4805 | -0.4975 |
| 대조군 4 op · 게이트 미적용 | -0.5176 | -0.5346 |

**✅ 대조군 판정: 겹친다 → 4.1 의 귀속 주장 성립.** 분리 폭이 규칙·게이트 네 조합 전부 음수다 (OWN 게이트 -0.4805 / OWN 미적용 -0.5176 / OF 게이트 -0.4975). 같은 분류 기준을 key-switch 연산에 적용하면 **+0.0282 (> 0, 완전 분리)** 다. 계단은 대조군에는 없고 key-switch 연산에만 있다 — digit 분해 구조로의 귀속이 성립한다.

**⚠️ 그러나 key-switch 쪽 분리는 분류 규칙에 의존한다 — 본문에 반드시 반영할 것.**

- 규칙 OWN(라이브러리별 자기 digit): 분리 폭 **+0.0282** → 분리 성립 (기존 표 3).
- 규칙 OF(OpenFHE digit 을 세 라이브러리에 일괄 적용): 분리 폭 **-0.2449** → **분리 소멸**.

소멸하는 이유는 잡음이 아니라 **설계**다. 프리셋이 라이브러리마다 `dnum` 을 다르게 준다 (예: preset C 는 OpenFHE `dnum=2`, Lattigo `dnum=4`). 그래서 digit 이 바뀌는 레벨 자체가 라이브러리마다 다르고, preset C 에서 OpenFHE 는 L6↔L5 한 번인데 Lattigo 는 L8↔L7·L4↔L3 두 번이다. OpenFHE 의 전이 레벨을 Lattigo 행에 갖다 붙이면 Lattigo 의 진짜 계단(g≈0.65)이 '비전이'로, 진짜 비전이(g≈0.90)가 '계단'으로 뒤집혀 라벨이 섞인다.

> **권고:** 표 3 의 계단 분류는 **라이브러리별 digit(규칙 OWN)** 으로 유지한다. 3.4절의 'digit 은 OpenFHE 만 실측' 이라는 단서는 **SEAL 에만** 적용해야 한다 — SEAL 의 `digit = level+1` 은 측정도 유도도 아닌 하드코딩이지만, Lattigo 의 digit 은 `min(dnum, ceil((L+1)/|P|))` 이라는 문서화된 공식에서 **파라미터로부터 유도**한 값이라 성격이 다르다. 본문이 두 경우를 같은 문장으로 묶고 있다면 분리해서 쓸 것.

## 2. 표 4 — 절편의 절대값

### 2.0 전제 확인

- 레벨 스윕 범위: **L1 … L(maxLevel)**. `level = 0` 인 행은 **0건** — 하네스가 `maxLevel..1` 만 훑기 때문이다(`CLAUDE.md` 측정 스펙). 따라서 아래 '바닥'은 전부 **L1** 을 뜻하며 L0 이 아니다.

- 적합 대상 행 수: preset 4 × library 3 × op 8 = **96** 조합, 조합당 레벨 수 A12/B6/C10/D4. 실제 조합 수 **96** **일치**
- 레벨 연속성은 §0 에서 확인 완료(불연속 0건, 중복 0건). 적합은 각 조합의 **전 레벨**을 쓴다.

### 2.1 ⚠️ 기존 적합 모형에 digit 이 들어가 있다

직전 분석의 `fit_coeffs.csv` 가 쓴 모형은

```
M2 :  mean_us ≈ a·(level+1)·digit + b      (digit 포함)
```

인데 `digit` 열의 성격이 라이브러리마다 다르다.

| library | digit 출처 | M2 에 넣으면 실제로 무슨 모형이 되나 |
|---|---|---|
| OpenFHE | 런타임 실측 (`GetNumPartQ`/`GetNumPerPartQ`) | 의도한 대로 `a·(L+1)·d + b` |
| Lattigo | 파라미터에서 유도 (`min(dnum, ⌈(L+1)/|P|⌉)`) | 의도한 대로 (단 실측 아님) |
| SEAL | `digit = level+1` **하드코딩** (`presetsearch_seal.cpp:169-171`) | `(L+1)·digit = (L+1)²` → **사실상 2차 모형**. 다른 두 라이브러리와 같은 모형이 아니다 |

즉 M2 로 세 라이브러리의 b 를 나란히 비교하면 **SEAL 만 2차식의 절편**을 비교하는 셈이다. 그래서 지시대로 digit 없는 단순 모형

```
M1 :  mean_us ≈ a·(level+1) + b          (digit 미사용)
```

으로 다시 적합해 두 모형을 나란히 놓는다. M1 은 세 라이브러리에 **문자 그대로 같은 모형**이다.

> **재산출 대조** — M2 를 다시 적합해 기존 `fit_coeffs.csv` 와 맞춰봤다. 기존 적합은 cv>0.05 인 레벨을 빼고 적합해서 96 조합 중 **22개**가 레벨을 일부 잃었다(key-switch 3종 중에는 preset B·SEAL·`mul_cc_rlk` 하나뿐, 5/6 레벨). 전 레벨을 쓴 74개 조합에서는 상대오차 최대 **4.80e-15** 로 **완전히 재현된다.** 아래 표는 게이트 없이 전 레벨을 쓴 값이다.

### 2.7 ⚠️ 전제 재검토 — SEAL 의 `digit = level+1` 은 '가짜'가 아니다

§2.1 에서 이 값을 '하드코딩'이라 적었고 직전 분석들도 그렇게 다뤄 왔다. M1 을 쓸지 말지가 여기 걸려 있어 **SEAL 원본을 직접 확인했다.**

`native/src/seal/evaluator.cpp` 의 `switch_key_inplace`:

```cpp
size_t decomp_modulus_size = parms.coeff_modulus().size();   // :2615  = 해당 레벨의 Q 프라임 수
size_t rns_modulus_size    = decomp_modulus_size + 1;        // :2618  = Q 프라임 + 특수소수 1개
...
SEAL_ITERATE(iter(size_t(0)), decomp_modulus_size, [&](auto J) { ... });   // :2677, :2783, :2819
```

key-switch 내부 루프가 도는 횟수가 `decomp_modulus_size` = **|Q| = level+1** 이다. SEAL 은 하이브리드 key-switching 을 쓰지 않고 **RNS 성분 하나당 digit 하나**로 완전 분해한다(특수소수는 1개, logP=60 고정). 하네스도 그 사실을 그대로 적어 뒀다 — `presetsearch_seal.cpp:225-227` `const size_t dnum = coeff.size() - 1;  // digit = Q 프라임 1개씩` / `// SEAL digit 수 = 해당 레벨의 Q 프라임 수 = level+1`.

> **정정:** `digit = level+1` 은 런타임 API 로 읽은 값이 아닐 뿐 **구조적으로 옳은 값**이다. 따라서 (a) M2 를 SEAL 에 적용해 2차식이 되는 것은 모형 오류가 아니라 **SEAL 의 key-switch 비용이 실제로 레벨의 2차이기 때문**이고, (b) 'SEAL 에 계단이 없다'는 동어반복이 아니라 **분해 수가 레벨마다 정확히 1씩 늘어 묶음(계단)이 생길 수 없다**는 실질적 사실이다. 이 정정은 §1 의 규칙 논의와 3.4절 서술에도 영향을 준다(범위 밖이므로 여기서는 표시만 한다).

### 2.8 판정 — 단순 모형 M1 은 결론을 유지하지 못한다

| 확인 항목 | M1 (digit 미사용) | M2 (digit 포함) |
|---|---|---|
| 절편 b < 0 인 적합 (key-switch 36개) | **28개** | 0개 |
| 절편 b < 0 인 적합 (8 op 96개) | **74개** | 0개 |
| R² 중앙값 (OpenFHE / Lattigo / SEAL) | 0.9705 / 0.9638 / 0.9812 | 0.9936 / 0.9921 / 0.9984 |
| R² 가 상대 모형보다 높은 적합 | **0/36** | 36/36 |
| `b(OpenFHE) > b(Lattigo)` 인 조합 | **3/12** (preset C 만) | 12/12 |

**❌ 유지되지 않는다. 세 가지가 동시에 어긋난다.**

1. **절편이 음수다.** M1 은 key-switch 적합 36개 중 **28개**, 8 op 전체 96개 중 **74개**에서 b < 0 이 나온다. 예: preset A · OpenFHE · `rot1` 의 b = -5,838 µs. 음수 절편은 '레벨을 0 까지 내리면 비용이 음수'라는 뜻이라 **고정비 바닥으로 해석할 수 없다.** 표 4 가 말하려는 것이 바로 그 바닥이므로, 이 모형으로는 표 자체가 성립하지 않는다.

2. **순서가 뒤집힌다.** M1 에서 `b(OpenFHE) > b(Lattigo)` 는 12개 조합 중 **3개**(preset C)뿐이고, A·B·D 에서는 Lattigo 의 절편이 더 크다. §2.6 의 z 검정도 M1 에서는 부호가 조합마다 갈린다. 즉 '**OpenFHE 의 고정비가 크다**' 는 4절의 핵심 주장이 M1 에서는 성립하지 않는다.

3. **적합도 자체가 나쁘다.** R² 는 36개 적합 **전부** M2 가 M1 보다 높다 (M1 중앙값 0.96~0.98 vs M2 0.99~0.998). 비용이 레벨에 대해 **볼록**하기 때문이다 — 직선을 억지로 맞추면 절편이 아래로 끌려 내려가고, 그게 1번의 음수 절편의 원인이다.

> **결론: 논문은 digit 포함 모형 M2 를 그대로 쓴다.** 지시에 있던 '단순 모형에서도 결론이 유지되면 3.4절의 digit 한계를 우회한다'는 경로는 **닫혔다.** 대신 §2.7 에서 그 한계 자체가 과장이었음이 확인됐다 — 세 라이브러리의 digit 은 모두 각자 알고리즘의 **실제 분해 수**이고, 문제는 '못 믿을 값'이 아니라 **세 값이 서로 다른 양이라 숫자를 나란히 비교하면 안 된다**는 것이다. 3.4절은 그 방향으로 고쳐 쓰면 되고, 표 4 의 b 는 M2 값을 그대로 실으면 된다.

### 3.1 어느 변종의 수치인가 — 본문 표는 `leveldrop` 을 쓴다

| 변종 | 뜻 | OpenFHE | Lattigo | SEAL |
|---|---|---|---|---|
| `leveldrop_ip` | 제자리 강하 (원본 소멸) | `LevelReduceInPlace` | `DropLevel` | `mod_switch_to_next_inplace` |
| `leveldrop_oop` | 새 암호문 반환 (원본 보존) | `LevelReduce` | `DropLevelNew` | `mod_switch_to_next` |
| `clone_only` | 깊은 복사만 (분해용 기준선) | `Clone()` | `CopyNew()` | 복사 생성자 |
| **`leveldrop`** | **각 라이브러리의 최저비용 경로** | = `_ip` | = `_ip` | **= `_oop`** |

`leveldrop` 이 SEAL 만 `_oop` 인 이유: SEAL 의 제자리 경로는 내부에서 임시 버퍼를 잡고 두 번 복사한다(`evaluator.cpp` 에 `// TODO: avoid copying and temporary space allocation` 주석이 그대로 있다). 그래서 SEAL 은 **제자리가 더 비싸고**, 실제 구현이라면 out-of-place 를 쓴다.

> **본문 표 5 에 쓸 변종: `leveldrop`.** 5절의 배치 규칙은 '암호문을 소비하며 레벨을 내린다'를 전제하므로, 각 라이브러리가 실제로 택할 최저비용 경로가 맞는 비교 대상이다. 다만 **세 라이브러리가 같은 API 형태를 쓰는 것은 아니다**(SEAL 만 out-of-place)라는 점을 표 각주에 밝힐 것.

### 3.4 ⚠️ 하강 비용의 비중 — 기존 보고값은 **분모가 다르다**

- (가) 병합 행 수: key-switch 3 op × 32 레벨 × 3 lib = **288** → 실제 **288** **일치**

**(가) 동일 레벨 key-switch 1회 비용 대비 (%)** — op 별 중앙값과 통합값

## 5. 4.4절 정밀도 수치 검증

### 5.1 지표가 정밀도 비트인가 오차 비트인가 — 소스 확인

`src/precision_common.h:44` (세 라이브러리 공용):

```cpp
inline double precision_bits(const std::vector<double> &got, const std::vector<double> &want)
{
    double s = 0; size_t n = want.size();
    for (size_t i = 0; i < n; i++) s += std::fabs(got[i] - want[i]);
    double mean_err = s / (double)n;
    if (mean_err <= 0) return 999.0;
    return -std::log2(mean_err);      // ← 평균 절대오차의 -log2
}
```

CSV 로 나가는 값은 `presetsearch_openfhe.cpp:481-488` 의 `prow(path, got, want)` 가 `precision_bits(got, want)` 를 그대로 적은 것이고, 호출은 두 번뿐이다 — `prow("enc_dec", dec(ct), x)` 와 `prow("rot1", dec(EvalRotate(ct,1)), want_rot)`. `ks_loss` 는 측정이 아니라 집계에서 만들어진다 — `scripts/v3_unify.py:68` `pv["ks_loss"] = pv["enc_dec"] - pv["rot1"]`.

| 열 | 정체 | 방향 | 대표값 |
|---|---|---|---|
| `enc_dec` | 암호화→복호 왕복의 **정밀도 비트** `−log₂(평균절대오차)` | **클수록 좋다** | 36.3 (preset C) |
| `rot1` | 회전 1회 뒤의 **정밀도 비트** | **클수록 좋다** | 32~33 (preset C) |
| `ks_loss` | `enc_dec − rot1` = key-switch 가 **까먹은 비트 수**. `log₂(오차_rot1 / 오차_encdec)` 와 같다 | **작을수록 좋다** | 3.3~4.1 (preset C) |

> **본문 문장의 첫 번째 오류가 여기서 확정된다.** 본문의 `4.09 → 3.28비트` 는 **`ks_loss`(손실 비트)** 값이지 정밀도 값이 아니다 — 이 데이터에서 정밀도(`enc_dec`/`rot1`)는 **32~36비트대**이고 4나 3 같은 값이 나올 수 없다. 게다가 `ks_loss` 는 작을수록 좋으므로 `4.09 → 3.28` 은 **정밀도가 나아진 것**이다. 본문이 "정밀도 변화"라고 부르면 방향이 거꾸로 읽힌다.

### 5.2 행 수 회계와 전제

- `v3_summary_precision.csv` 전체 **2304행** → `mode == '1t'` 필터 후 **1152행**.

집계 방식(rep 중앙값/평균) × 지표 3종 × 통계 3종 × C·OpenFHE 포함/제외 = 36개 조합을 전수로 훑어 대조했다.

- digit 전이: **L6↔L5** (2 → 1), 관측 창 안에 **1회**.
- 정밀도 계단: **L5↔L4** (§5.6).
- **어긋남: 정확히 1 레벨.** digit 은 L6↔L5 에서 바뀌는데 `rot1` 정밀도는 L5↔L4 에서 바뀐다. L5 는 digit 이 이미 1 로 내려온 레벨인데 정밀도는 아직 높은 레벨 쪽 평지에 남아 있다.

> 따라서 **이 계단을 digit 전이로 귀속시킬 수 없다.** 본문이 두 현상을 연결하려면 1 레벨 어긋남을 설명해야 하는데 이번 분석에는 그 근거가 없다. 4.1 의 비용 계단(= digit 전이에서 정확히 일어남)과 **다른 현상으로 분리해서 서술할 것.**
