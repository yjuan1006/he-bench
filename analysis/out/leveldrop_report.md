## 1. 1단계 — API 확인 (스케일을 바꾸지 않고 레벨만 낮추는 연산)

| library | 함수 | 스케일보존 | 레벨인자 | 형태 |
|---|---|---|---|---|
| openfhe | `CryptoContext::LevelReduce(ct, evalKey, levels=1)` / `LevelReduceInPlace(...)` | 예 | 예 (`levels`, 기본 1) | `LevelReduce` = Clone + in-place (새 암호문) / `LevelReduceInPlace` = 제자리 |
| lattigo | `ckks.Evaluator.DropLevel(ct, levels)` / `DropLevelNew(ct, levels)` | 예 | 예 (`levels`) | `DropLevel` = 제자리 / `DropLevelNew` = CopyNew + DropLevel |
| seal | `Evaluator::mod_switch_to_next(ct, dst)` / `mod_switch_to_next_inplace(ct)` | 예 | **아니오 — 1단계 고정** | 둘 다 있음. ⚠️ 제자리 쪽이 **더 비싸다**(임시 버퍼 + 2회 복사) |

### 1.1 스케일 보존 근거 (소스)

**OpenFHE** — `src/pke/lib/scheme/ckksrns/ckksrns-leveledshe.cpp`

```cpp
// ModReduceInternalInPlace (= Rescale 의 알맹이)  : 스케일을 나눈다
    dcrtpoly.DropLastElementAndScale(...);
    ciphertext->SetScalingFactor(ciphertext->GetScalingFactor() / modReduceFactor);

// LevelReduceInternalInPlace (= LevelReduce 의 알맹이) : 스케일을 손대지 않는다
void LeveledSHECKKSRNS::LevelReduceInternalInPlace(Ciphertext<DCRTPoly>& ciphertext, size_t levels) const {
    for (auto& element : ciphertext->GetElements())
        element.DropLastElements(levels);
    ciphertext->SetLevel(ciphertext->GetLevel() + levels);
}   // ← SetScalingFactor 호출이 없다
```

⚠️ `LevelReduceInPlace` 는 `ScalingTechnique == FIXEDMANUAL` 에서만 실제로 동작한다(`rns-leveledshe.cpp:339-343`). 이 하네스는 FIXEDMANUAL 이라 조건을 만족하지만, 그래도 **레벨을 매 측정마다 검증**한다(§2).

**Lattigo v6.2.0** — `schemes/ckks/evaluator.go:465-469`

```go
// DropLevel reduces the level of op0 by levels and returns the result in op0.
// No rescaling is applied during this procedure.
func (eval Evaluator) DropLevel(op0 *rlwe.Ciphertext, levels int) {
	op0.Resize(op0.Degree(), op0.Level()-levels)
}
// ring/poly.go:48  Resize → pol.Coeffs = pol.Coeffs[:level+1]   (슬라이스 절단, 산술 없음)
```

**SEAL 4.3** — `native/src/seal/evaluator.cpp:1382-1414`, `1282-1344`

```cpp
case scheme_type::ckks:
    // Modulus switching without scaling
    mod_switch_drop_to_next(encrypted, destination, std::move(pool));
...
    destination.scale() = encrypted.scale();   // ← 스케일을 그대로 복사
// 반면 rescale_to_next → mod_switch_scale_to_next (스케일을 나눈다). 별개 함수다.
```

### 1.2 ⚠️ 세 라이브러리의 작업량은 대응하지 않는다

| library | 가장싼형태 | 하는일 | 복잡도 |
|---|---|---|---|
| openfhe | in-place | 타워 1개 해제(`m_vectors.resize`) + 파라미터 객체 재생성 | O(1) 해제 · 산술 없음 |
| lattigo | in-place | 슬라이스 길이만 줄임(`Coeffs[:level+1]`) | O(1) · 메모리 해제조차 없음 |
| seal | **out-of-place** | 남는 RNS 성분을 새 버퍼로 복사(`set_uint`) | **O(N·L)** 복사. O(1) 강하가 없다 |

따라서 `leveldrop` 열은 **"그 라이브러리가 레벨을 내리는 가장 싼 정당한 방법"** 이지 같은 작업량의 비교가 아니다. 작업량이 대응하는 비교는 `leveldrop_oop`(세 라이브러리 모두 새 암호문을 하나 만든다) 쪽이다. 두 값을 모두 낸다.

측정 op 4종:

| op | 뜻 |
|---|---|
| `leveldrop` | 그 라이브러리의 **가장 싼** 1레벨 강하. openfhe·lattigo = in-place, seal = out-of-place |
| `leveldrop_ip` | 제자리 형태 |
| `leveldrop_oop` | 새 암호문 반환 형태 |
| `clone_only` | 암호문 깊은 복사만 (분해용: `leveldrop_oop ≈ clone_only + leveldrop_ip` 인지 확인) |

## 3. 행 수 회계 · 타이머 분해능 처리

- 프리셋별 레벨 수: A=12, B=6, C=10, D=4 → 합 **32**
- 기대 행 수 = 레벨합 32 × 라이브러리 3 × op 4 = **384**  →  실제 **384행** (일치)
- 검증 행 = 레벨합 32 × 라이브러리 3 = **96**  →  실제 **96행** (일치)
- 레벨 연속성: 결측/중복 0건

### 3.1 타이머 분해능 — 배치 계측이 필요했는가

본측정 전에 예비 실행으로 확인했다(이 저장소 dku16c, 코어 12 고정):

| 시계 | 호출 쌍의 최소 간격 | 중앙값 |
|---|---|---|
| C++ `std::chrono::steady_clock` | **40 ns** | 44 ns |
| Go `time.Now()` | **86 ns** | 90 ns |

Lattigo 의 제자리 강하는 슬라이스 절단이라 실측 **23~121 ns** 다 — **Go 시계의 호출 오버헤드(86ns)보다 싸다.** 단발 계측이 원리적으로 불가능하다.

**처리 방식 (배치 계측).** 타이머 밖에서 K개 사본을 만들고 타이머 안에서 K회를 수행한 뒤 K로 나눈다. 이 rep 값을 30번 반복해 평균·표준편차를 낸다. K 는 암호문 크기로 정한다 (예산 64MB / `2·(L+1)·N·8` 바이트, 4≤K≤2048).

- 제자리 강하는 **파괴적**이라 같은 암호문에 반복할 수 없다 — 배치는 분해능뿐 아니라 이 이유로도 필요하다.
- ⚠️ 배치 rep 의 `std_us` 는 "K개 평균"의 rep 간 산포라 단발 계측의 std 와 **의미가 다르다** (약 1/√K 로 줄어든다). CSV 의 `rep_mode`(single/batch)·`batch_k` 열로 구분한다.

**결론에 미치는 영향:** §6 의 판정은 `drop_cost` 가 `step_gain` 보다 **3~5자릿수 작다**는 사실에만 의존한다(§6.3 의 비용비 표). drop_cost 가 2배·10배 틀려도 net 의 부호는 바뀌지 않는다 — 부호가 바뀌려면 §6.3 의 비용비 역수만큼 (가장 비싼 SEAL 에서도 32배, Lattigo 는 8000배 이상) 틀려야 한다. 따라서 cv 게이트 결과는 판정을 흔들지 않는다.

## 8. 판정 — 5절 정지 조건에 대해

> §1~§7 표는 스크립트가 자동 산출한 숫자다. 아래는 그 숫자를 읽고 쓴 **결론**이다.

### 8.1 순수 레벨 강하는 얼마인가 — 라이브러리별로 **4자릿수** 차이가 난다

| library | min_us | max_us |
|---|---|---|
| lattigo | 0.023 | 0.121 |
| openfhe | 0.921 | 2.02 |
| seal | 5.292 | 363 |

- **Lattigo** — 슬라이스 절단이라 산술도 메모리 해제도 없다. 사실상 **공짜**다.
- **OpenFHE** — 타워 1개 해제 + 파라미터 객체 재생성. **레벨과 거의 무관하게 ~1~2μs** 로 평평하다(전 프리셋·전 레벨). 강하 비용을 레벨 상수로 봐도 되는 유일한 경우다.
- **SEAL** — O(1) 강하가 **없다**. 남는 RNS 성분을 복사해야 해서 비용이 **레벨에 비례**한다(프리셋 A 에서 L1 10.7μs → L12 363μs, 34배). add_cc 의 0.30배 수준이다.

이것 자체가 논문 주제(레벨-비용 프로파일의 라이브러리 의존성)의 사례다: **같은 의미의 연산이 한쪽에서는 레벨 상수, 다른 쪽에서는 레벨 비례다.**

### 8.2 "계단 하나를 건너 얻는 이득 > 강하 비용" 이 성립하는 구간

**주 지표 기준으로 252쌍 중 251쌍에서 성립한다.** `n_break`(강하를 회수하는 데 필요한 후속 key-switch 연산 수)는 **네 프리셋·세 라이브러리·세 op 전부에서 1** 이다 — 강하 뒤 key-switch 를 **한 번만** 해도 본전을 넘는다.

- 비용비 `drop/gain` 중앙값: OpenFHE 0.039% · Lattigo 0.0025% · SEAL 2.42%. 가장 비싼 SEAL 조차 최대 3.1% 다.
- 계단 전이에서는 이득이 더 커서 비율이 더 낮다(OpenFHE 계단 0.022% vs 비계단 0.044%).

**유일한 예외 1쌍**: preset A · Lattigo · `mul_cc_rlk` · L11→L10. 여기서 net<0 인 것은 강하 비용(0.097μs) 때문이 **아니라** `step_gain` 자체가 **음수(−527μs)** 이기 때문이다 — 기존 v3 8-op 자료에서 레벨을 내렸는데 오히려 느려진 그 쌍(g=1.010)이다(`analysis/out/level_cost_report.md` §5 에서 이미 확인된 이상치). **강하 비용의 문제가 아니다.**

### 8.3 그래서 5절의 정지 조건은 무엇이 지배하는가

**강하 비용이 아니다.** 이 측정의 결론은 "강하는 싸다" 가 아니라 **"강하 비용은 정지 조건을 결정하는 항이 아니다"** 이다. 후속 key-switch 1회면 회수되므로, 경제적 손익분기는 실질적으로 항상 만족된다. 따라서 5절의 정지 조건은 비용이 아니라 **남은 레벨 예산(곱셈 깊이)과 정밀도**가 결정한다고 써야 한다. 배치 규칙은 "내려도 되는가(비용)" 가 아니라 "내릴 레벨이 남아 있는가 · 내려도 정밀도가 버티는가" 로 정식화되어야 한다.

⚠️ **단, 원본 암호문을 보존해야 하는 배치에서는 결론이 바뀐다.** 새 암호문을 만드는 `leveldrop_oop` 기준으로는 net≤0 이 3쌍 나온다 (전부 preset A · Lattigo · L11→L10). 깊은 복사가 이득을 잡아먹기 때문이다. 5절에서 강하를 **제자리로 하는지 사본을 남기는지 명시**해야 한다.

### 8.4 인용 시 반드시 함께 밝힐 것

1. `leveldrop` 은 라이브러리마다 **다른 작업**이다(§1.2). 세 값을 나란히 두고 "SEAL 이 느리다" 고 쓰면 안 된다 — SEAL 은 O(1) 강하 API 가 없어서 더 많은 일을 한다. 작업량이 대응하는 비교는 `leveldrop_oop` 쪽이다.
2. `rep_mode=batch` 행의 `std_us` 는 단발 계측의 std 와 의미가 다르다(§3.1).
3. **Lattigo 의 `leveldrop_oop`·`clone_only` 는 신뢰하지 말 것.** `oop/(clone+ip)` 비가 0.45~3.95 로 튄다(§5.1) — Go GC 가 6.8MB 할당을 30 reps 안에서 불규칙하게 처리한 결과다. OpenFHE 는 같은 비가 0.98~1.05 로 안정적이다.
4. mt 는 재지 않았다(범위 밖). 이 결과는 **1t 전용**이다.
